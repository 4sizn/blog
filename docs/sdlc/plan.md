### 2-1. 선행 관계

```
W-01 (골격 템플릿) ─┬─→ W-02 (매핑 실측)
                    ├─→ W-03 (placeholder) ─┬─→ W-04 (draft 초안화)
                    │                        └─→ W-15 (다중 릴리즈 조회) ─┐
                    └─→ W-06 (skill 골자) ─┬─→ W-07 (입력원 3종)          │
                                            ├─→ W-08 (부속 규칙) ─┐        │
                                            ├─→ W-17 (humanize 강제) ┤     │
                                            └─→ W-09 (발동 테스트)  │     │
                                                                    ↓     ↓
                                              W-10 (screen-saver 2건) ─┬─→ W-11 (blog 2건) ─┐
                                                                        ├─→ W-12 (ai-config 3건) ─┤
                                                                        └─→ W-16 (누락 2건) ─────┴─→ W-13 (전체 검증)

W-05 (워크플로 경로) ─→ W-14 (CLAUDE.md)      ← W-01과 병렬 가능
```

- **W-17(humanize 강제)이 모든 글 작성의 선행 조건이다.** 문장 경로가 확정되기 전에 글을 쓰면 다시 써야 한다
- W-16(누락 2건)은 W-15(다중 조회) 이후에 둔다. 스크립트가 초안을 만들어주면 그 위에서 다듬는다

- **W-01이 임계 경로의 시작점이다.** 골격이 흔들리면 W-03·W-06·W-10 이후가 전부 흔들린다
- W-05·W-14는 골격과 무관해 언제든 병렬 처리 가능
- W-10을 W-11·W-12보다 먼저 두는 이유: 로컬 레포가 있어 근거 확보가 쉽고, skill을 실제로 써보는 첫 시험대가 된다 (dogfooding)

## 3. 일정

날짜는 미정이다. 개인 블로그 작업이라 달력 일정보다 **작업 세션 단위**로 잡는다.
아래 S1~S4는 연속된 날짜가 아니라 "한 번 앉아서 하는 묶음"이다.

| 세션 | 포함 WBS | 예상 | 산출물 | 검증 |
|------|---------|------|--------|------|
| S1 — 골격 확정 | W-01, W-02, W-05 | 3h | 템플릿, 매핑표, 워크플로 수정 | 매핑 불가 0건 확인 + 워크플로 로컬 재현 |
| S2 — 파이프라인 | W-03, W-04, W-15, W-14 | 4.5h | 스크립트 수정(placeholder·draft·다중 조회), `CLAUDE.md` | placeholder 집합 비교 + draft filtered out + 5건 전부 생성 확인 |
| S3 — skill | W-06, W-07, W-08, W-17, W-09 | 6.5h | `SKILL.md`, `.gitignore` | 신규 세션 발동 테스트 3/3 + humanize 경유 리허설 1건 |
| S4 — 이미지 확보 | W-20, W-19, W-18 | 6h | `static/screen-saver` 재사용 판정 + `static/blog/` + `static/ai-config-monitor/` | 장당 300KB 이하 + 다크·라이트 렌더링 확인 |
| S5 — 글 작성 | W-10, W-11, W-12, W-16, W-13 | 9h | 보정 7건 + 누락 2건 = 글 9건 | 골격 통과 + 사실 대조 + 빌드 + 눈검증 |

**검증·리뷰 시간은 각 세션 예상에 포함돼 있다.** S1의 3h 중 1h, S5의 9h 중 1h이 검증이다.
S5가 커지면 프로젝트별로 쪼갠다 (screen-saver 2건 → blog 2건 → ai-config-monitor 5건).
**S4를 S5보다 앞에 두는 이유**: 이미지가 먼저 있으면 글을 쓰면서 무엇을 보여줄지 정할 수 있다.
글을 먼저 쓰면 나중에 이미지를 끼워 맞추게 되고, 그 순서가 억지 장식 이미지를 만든다.
`/sdlc:review`·`/sdlc:test` 를 별도로 돌린다면 세션당 0.5~1h를 더 잡는다.

## 7. 요구사항 갱신 — 처리 결과

계획 수립 중 발견해 제안한 2건과 사용자 추가 지시 1건이 **2026-08-11 모두 요구사항에 반영됐다.**

| 제안 | 결정 | 반영 |
|------|------|------|
| 제안 1 — 릴리즈 동기화 누락 | **A 채택** (스크립트 수정 + 누락 2건 작성) | FR-12 · D-07 · W-15 · W-16 |

아래는 제안 당시의 근거 기록이다.

### 제안 1 — 릴리즈 동기화 누락 (근거 있음) → **채택 (A)**

**사실** (2026-08-11 조회): `ai-config-monitor` 의 GitHub 릴리즈는 5건(`v1.2.0`·`v1.2.1`·`v1.2.2`·`v1.2.3`·`v1.2.4`)
인데 블로그에는 3건만 있다. `v1.2.1`·`v1.2.3` 이 없다.

**원인**: `scripts/sync-releases.mjs:51` 이 `releases/latest` 만 조회한다. cron은 하루 한 번 돌고
그 시점의 latest만 가져오므로, 같은 날 두 번 릴리즈하면 앞엣것이 영구히 누락된다.
(실제로 v1.2.0~v1.2.2가 2026-02-23 하루에, v1.2.3~v1.2.4가 2026-02-24 하루에 나왔다)

**제안**: `releases/latest` → `releases?per_page=N` 으로 바꿔 미동기화 릴리즈를 모두 잡는다.
누락된 2건을 새 골격으로 채워 넣는 것까지 포함할지는 별도 판단이 필요하다.

**2026-08-11 A 채택** — 스크립트를 목록 조회로 고치고(W-15), 누락 2건도 새 골격으로 작성한다(W-16).

### 제안 2 — 릴리즈 노트 날짜 폴백 규칙 → **채택**

**사실**: 릴리즈 노트의 날짜는 지금 GitHub 릴리즈의 `published_at` 에서 온다.
GitHub 릴리즈가 없는 프로젝트(App Store 앱)는 근거가 될 날짜가 정의돼 있지 않다.

**제안** (2026-08-11 사용자 지시 반영): 날짜 우선순위를 골격 규칙으로 못 박는다.

1. GitHub 릴리즈의 `published_at`
2. 없으면 해당 버전 태그의 커밋 날짜
3. 태그도 없으면 **소스 마지막 업데이트 일자** (`pushedAt` 또는 로컬 마지막 커밋)

`requirements.md` 부록 A-6에 이 순위를 넣었고, skill 절차(W-07)에서 쓴다. WBS 증가 없음 (기존 작업에 흡수).

### 추가 지시 — `humanize-korean` 경유 강제 → **채택**

**지시** (2026-08-11): 릴리즈 노트 문장은 `im-not-ai` 플러그인의 `humanize-korean` 스킬로 작성하도록 강제한다.

**확인한 사실**: 스킬 이름은 `humanize-korean` v2.3.0, 호출은 `humanize-korean:humanize-korean`.
"내용은 한 글자도 건드리지 않고 문체·리듬·표현만" 재작성한다고 명시돼 있어 사실 문서에 쓸 수 있다.
경로는 light/standard/heavy 3종이며 "정밀 모드"·`--strict` 로 heavy를 고정할 수 있다.

**함께 처리해야 하는 것**: 이 스킬은 cwd에 `_workspace/{run_id}/` 를 만든다 → 저장소 오염 방지가 필요하다 (R-10, W-17).
또 필수 경유로 못 박은 만큼 **스킬이 없으면 글을 쓸 수 없다** → 부재 시 우회하지 말고 멈추는 규칙을 둔다 (R-11).
