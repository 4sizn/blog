# 블로그 릴리즈 노트 골격 + 작성 skill 요구사항 정의서

## 1. 배경 · 목적

4sizn 블로그의 릴리즈 노트는 `content/blog/releases/` 한 폴더에 쌓이지만, 만들어지는 경로가 두 갈래다.

| 경로 | 산출 방식 | 글 수 (2026-08-11) |
|------|----------|-------------------|
| 자동 | `scripts/sync-releases.mjs` + `content/templates/new_releases.md`, 매일 00:00 UTC cron | 7건 |
| 수동 | 사람이 처음부터 작성 | 4건 |

**문제 1 — 자동 경로의 결과물이 읽을 글이 아니다.** 스크립트는 GitHub 릴리즈 본문의 리스트 항목을
conventional commit 프리픽스로 5분류해 그대로 나열한다. 서사가 없고, 릴리즈 본문에 같은 내용이 중복돼 있으면
그대로 중복된다. 예: `2026-02-04-screen-saver-extension-1.0.6.md`는 "기타 변경사항" 한 섹션에 제한 도메인
목록이 두 번 겹쳐 나온다.

**문제 2 — 수동 경로에 골격이 없다.** 품질은 좋지만 섹션 구성이 글마다 다르다.

| 글 | 섹션 구성 |
|----|----------|
| Garden Eel Cove v1.6.0 | 주요 기능 / 개선사항 / 버그 수정 / 지원 플랫폼 / 설치 / 관련 링크 / 작성자 |
| Lonely Candle v1.2 | 주요 기능 / 이번 버전 / 지원 플랫폼 / 다운로드 / 작성자 |
| Swing Golf v1.2 | 주요 기능 / 이번 버전 / **버전 히스토리** / 지원 플랫폼 / 다운로드 / 작성자 |
| Screen Saver 스토어 등록 준비 | 이유 / 스크린샷 / 제작 방식 / 용량 / 제출 문서 / 남은 일 / 관련 링크 / 작성자 |

**문제 3 — 자동 동기화가 커밋·푸시에 도달하지 못한다.** (2026-08-11 확인)
`scripts/sync-releases.mjs:219`는 `content/blog/releases/`에 파일을 쓰지만,
`.github/workflows/sync-releases.yml`의 변경 감지·`git add`·요약 단계는 모두 `content/releases/`를 가리킨다.
그 경로는 존재하지 않고, `git status --porcelain content/releases/`는 경고만 낸 뒤 **빈 출력 + exit 0**을
반환한다. 따라서 `has_changes`는 항상 `false`가 되어 새 릴리즈가 생성돼도 커밋되지 않는다.

**목적**

1. 모든 릴리즈 노트가 공유하는 **골격**(필수·선택 섹션, frontmatter 스키마, 톤 규칙)을 정의한다.
2. 그 골격대로 쓰게 하는 **skill**을 만든다. 자동 생성물은 "초안"으로 격하하고, 사람이 skill로 완성한다.
3. 자동 경로를 골격에 맞춰 정합하고, 죽어 있는 파이프라인을 되살린다.

## 2. 범위

**In scope**

- 공통 골격 템플릿 — `content/templates/new_releases.md` 를 새 골격으로 교체
- 작성 skill — `.claude/skills/blog-release-note/SKILL.md` 신규 (프로젝트 로컬, git 추적)
- `scripts/sync-releases.mjs` 의 placeholder 계약을 새 템플릿에 맞춰 갱신
- 자동 생성물을 `draft: true` 초안으로 만들고, 사람이 다듬은 뒤 게시하는 흐름
- `.github/workflows/sync-releases.yml` 의 경로 불일치 수정
- 기존 자동 생성 글 **7건 전부** 새 골격으로 소급 보정
  (`blog-1.0.0`, `blog-1.0.1`, `screen-saver-extension-1.0.4`, `screen-saver-extension-1.0.6`,
  `ai-config-monitor-1.2.0`, `ai-config-monitor-1.2.2`, `ai-config-monitor-1.2.4`)
- GitHub 릴리즈가 없는 프로젝트(App Store 앱 등)의 수동 작성 흐름을 skill에 포함
- 버전 릴리즈가 아닌 마일스톤 글(예: 스토어 등록 준비)의 처리 규칙
- 릴리즈 노트 작성 시 `content/projects/<slug>.md` 의 최신 상태·링크 갱신 규칙
- `CLAUDE.md` 의 낡은 경로 기술 정정 (`content/releases/` → `content/blog/releases/`)
- **릴리즈 동기화의 다중 릴리즈 지원** — `releases/latest` 만 조회해 누락되는 구조를 고치고, 누락된
  `ai-config-monitor` v1.2.1·v1.2.3 두 건을 새 골격으로 작성한다 (2026-08-11 제안 1-A 승인)
- **`humanize-korean` 스킬 경유 강제** — skill의 본문 문장 작성 단계는 `im-not-ai` 플러그인의
  `humanize-korean` 스킬을 반드시 거친다 (2026-08-11 사용자 지시)
- 릴리즈 노트 날짜 폴백 규칙 (`published_at` → 태그 커밋 날짜 → 소스 마지막 업데이트 일자)
- **이미지 제작** — 소급 보정 9건 전부에 이미지를 넣는다. `ai-config-monitor` 5건은 터미널 UI를 직접
  캡처하고, `4sizn-blog` 2건은 당시 커밋을 재현해 캡처한다 (2026-08-11 D-10·D-11)

**Out of scope** — 이번에 하지 않는 것

- 수동 작성 글 4건 재집필 (`gardeneel-desktop-1.6.0`, `lonely-candle-1.2`, `swing-golf-1.2`,
  `screen-saver-extension-store-assets`) — 이미 골격에 가깝다. 골격 확정 후 별건으로 판단한다
- `content/blog/log`·`content/blog/dev` 등 릴리즈 노트 외 글의 템플릿·skill
- Quartz 레이아웃·스타일·컴포넌트 변경 (`quartz/` 하위 코드)
- `tracked-repos.json` 에 새 저장소 추가
- 영문 등 다국어 릴리즈 노트 (2026-08-11 확정 — D-03)
- App Store Connect API 연동 (앱 릴리즈 정보 자동 수집)
- `main` 푸시 배포가 `DEPLOY_TOKEN` 없이 실패하는 문제
- 기존 릴리즈 노트 URL 변경 (파일명 규칙은 유지한다 — 6절 제약)

## 6. 제약

- **Quartz v4.5.2 frontmatter 스키마** 를 벗어날 수 없다. `title`·`description`·`tags`·`aliases`·`draft`·
  `lang`·`enableToc`·`cssclasses`·`socialImage`·`created`·`updated` 는 실제로 쓰이는 필드다
- **파일명 규칙 유지**: `{YYYY-MM-DD}-{repo}-{version}.md`. 기존 글의 URL이 바뀌면 안 된다
- **콘텐츠 루트는 `content/`** 다. 빌드는 `content/` 만 읽는다 (`docs/` 는 Quartz 자체 문서로 빌드 대상 아님)
- **GitHub API 미인증 rate limit 60회/시간**. `tracked-repos.json` 의 4개 저장소는 GitHub 릴리즈 기반이고,
  App Store 앱 2종(Swing Golf, Lonely Candle)은 GitHub 릴리즈가 없다
- **skill은 프로젝트 로컬** 이므로 `4sizn-blog` 세션에서만 발동한다. 다른 저장소에서 작업 중 릴리즈 노트를

## 부록 A — 릴리즈 노트 골격 (설계 입력)

출처: 2026-08-11 사용자 제안 골격 + 기존 11건 매핑 검증에서 드러난 보완 4종.
**최종 문구와 placeholder 계약은 설계 단계에서 확정한다.** 여기서는 섹션 집합과 순서, 각 섹션의 판정 기준을 고정한다.

### A-0. 제목은 본문에 h1을 쓰지 않는다

Quartz는 frontmatter의 `title` 을 페이지 h1으로 렌더한다. 따라서 본문에 `# Project v1.2.0 — …` 을 쓰면
h1이 두 개가 된다. 제안 골격의 `# Project v1.2.0 — 릴리즈 한 줄 설명` 은 다음과 같이 나눠 배치한다.

| 제안 골격의 요소 | 실제 배치 |
|---|---|
| `Project v1.2.0` | frontmatter `title: "[YYYY-MM-DD] [Display Name] vX.Y.Z 릴리즈"` |
| `— 릴리즈 한 줄 설명` | frontmatter `description` + 본문 요약 헤딩 `## 🎉 [Display Name] vX.Y.Z 릴리즈` 아래 도입부 |

### A-1. 섹션 구성

| # | 섹션 | 필수 | 목적 | 비었을 때 |
|---|------|------|------|----------|
| 1 | Hero Image | **필수** (FR-10) | 이번 릴리즈를 한 장으로 보여준다 | CLI·도구도 터미널 화면을 캡처한다 (부록 A-8). 어떤 이미지도 사실을 보여주지 못할 때만 생략하고, 그 이유를 기록한다 |
| 2 | 도입부 2~3문장 | **필수** | "vX.Y.Z을 공개합니다. 이번 버전에서는 ___에 집중했습니다." | 쓸 말이 없으면 릴리즈 노트를 쓸 이유부터 다시 본다 |
| 3 | `⚠️ Breaking Changes` | 선택 | 깨지는 것을 가장 먼저 알린다 | 없으면 섹션째 삭제. **Under the Hood에 묻지 않는다** |
| 4 | `🎯 What it is` | 선택 | 제품 자체 소개 (첫 공개 릴리즈에서만) | 두 번째 이후 릴리즈는 생략 |
| 5 | `✨ What's New` | **필수** | 기능별 `###` + 왜/무엇이 달라졌는지 + 이미지 (A-2) | 기능 추가가 없는 릴리즈는 섹션을 생략하고 Improvements로 시작한다 |
| 6 | `🔧 Improvements` | 선택 | 목록. 기능이라 부르기 작은 개선 | |
| 7 | `🐛 Bug Fixes` | 선택 | 목록. 증상 기준으로 쓴다 (커밋 메시지 금지) | |
| 8 | `⚙️ Under the Hood` | 선택 | 성능·의존성·내부 구조 변경 | |
| 9 | `💻 Platforms` | 선택 | 지원 OS·최소 버전·배포 상태 | 앱·데스크톱 프로젝트용 |
| 10 | `📜 Version History` | 선택 | 이전 버전 표 | 버전이 잦은 프로젝트(앱)용 |
| 11 | `🔜 What's Next` | **필수** | 다음 버전 방향 | 미정이면 "미정"이라 쓴다. 지키지 못할 약속을 채우지 않는다 |
| 12 | `🚀 Try it` | **필수** | 다운로드·저장소·문서 링크 | |

작성자 섹션은 두지 않는다 (D-04). 헤딩은 영어로 쓴다 (D-05).

### A-2. What's New 하위 구조 (기능 하나당)


매핑 불가: **0건**

### A-4. 마일스톤 변형 (FR-08)

버전 릴리즈가 아닌 글(예: `2026-08-11-screen-saver-extension-store-assets`)은 같은 골격을 쓰되 다음을 지킨다.

- 제목에 버전을 붙이지 않는다 — `[YYYY-MM-DD] [Display Name] <무엇을 했는지>`
- 도입부에 **"새 버전 릴리즈는 아니다"** 를 명시한다
- `✨ What's New` → 이번에 한 일. `🔜 What's Next` → 남은 일 (체크박스 허용)
- 파일명은 버전 자리에 slug를 넣는다 — `{YYYY-MM-DD}-{repo}-{slug}.md`

### A-5. frontmatter (Quartz v4.5.2 실사용 필드)

```yaml
title: "[YYYY-MM-DD] [Display Name] vX.Y.Z 릴리즈"
description: "한 문장. 검색 결과·OG 카드에 그대로 쓰인다"
socialImage: "/static/<slug>/hero.jpg"   # 선택 — Hero Image가 있을 때
tags: [release, <category>, <repo>]
aliases: ["<Display Name> <version>", "<Display Name> 릴리즈"]
draft: true          # 자동 초안. 사람이 완성한 뒤 제거해 게시 (FR-04)
lang: ko
enableToc: true
cssclasses: [release, changelog]
created: YYYY-MM-DD  # 소급 보정 시 유지 (D-01)
updated: YYYY-MM-DD
```

### A-6. 날짜 결정 우선순위 (D-09)

파일명·`created` 에 쓰는 날짜는 다음 순서로 정한다. 위에서 얻으면 아래는 보지 않는다.

1. GitHub 릴리즈의 `published_at`
2. 해당 버전 태그의 커밋 날짜 (`git log -1 <tag>` 또는 `gh api repos/{owner}/{repo}/git/refs/tags/{tag}`)
3. **소스 마지막 업데이트 일자** — `gh repo view --json pushedAt` 또는 로컬 마지막 커밋 날짜

App Store 앱처럼 GitHub 릴리즈가 없는 프로젝트는 2번 또는 3번으로 내려간다.
어느 단계에서 얻었는지 작업 기록에 남긴다 — 나중에 날짜가 이상해 보일 때 근거를 되짚을 수 있어야 한다.

### A-7. 문장 작성 경로 (D-08 / FR-13)

본문 문장은 **초고 → `humanize-korean` 윤문 → 사실 대조 → 게시** 순서로만 만든다.

```
1. skill이 골격에 맞춰 초고를 쓴다 (사실·구조 확정)
2. humanize-korean 스킬로 윤문한다 (im-not-ai 플러그인 v2.3.0)
   - 정밀이 필요하면 "정밀 모드"/--strict 로 heavy 경로 고정
3. 윤문 결과와 초고의 사실 항목을 대조한다
   — 버전·날짜·수치·기능명·링크가 한 글자도 달라지지 않았는지 확인
4. 대조를 통과한 문장만 content/blog/releases/ 에 넣는다
```

- 이 경유는 **선택이 아니다.** 짧은 패치 릴리즈에도 적용한다
- `humanize-korean` 은 cwd에 `_workspace/{run_id}/` 를 만든다. 이 산출물은 저장소에 남기지 않는다
  (`.gitignore` 처리 또는 블로그 저장소 밖에서 실행 — 설계 단계에서 확정)
- 윤문 run_id는 작업 기록(`implementation.md`)에 남긴다

### A-8. 이미지 확보 방법 (D-10 / FR-10)

모든 릴리즈 노트는 이미지를 최소 1장 갖는다. 프로젝트 유형별로 확보 경로가 다르다.

| 유형 | 대상 | 확보 방법 |
|------|------|----------|
| 브라우저 확장 | `screen-saver-extension` | 스토어 등록 스크린샷 재사용 (`static/screen-saver/`) 또는 로컬 빌드 후 확장 실행 화면 캡처 |
| CLI · 터미널 UI | `ai-config-monitor` | 저장소를 클론해 빌드(`bun`)·실행하고 **터미널 화면을 캡처**한다. README·릴리즈 자산에 이미지가 없음을 확인했다 (2026-08-11) |
| 이 블로그 자체 | `4sizn-blog` | **당시 커밋을 worktree로 체크아웃해 빌드·캡처한다** (D-11). 현재 화면을 당시 모습처럼 쓰지 않는다 |
| 데스크톱 · 모바일 앱 | `gardeneel-desktop`, App Store 앱 | 앱 실행 화면 또는 스토어 스크린샷 |

**공통 규칙**

- 저장 위치: `quartz/static/<project-slug>/` — 프로젝트별로 폴더를 나눈다
- 용량: 장당 **300KB 이하** (NFR-03). PNG가 크면 JPEG(품질 ~82)로 변환한다
- 대체 텍스트: 무엇을 보여주는 화면인지 한 문장으로 적는다. `![스크린샷]` 같은 빈 alt는 쓰지 않는다
