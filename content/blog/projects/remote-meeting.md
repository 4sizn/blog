> **근거 범위**: 2022년 3월 7일~14일에 공개한 RemoteMeeting 기술 회고 Day0·1·2·4·5를 분석해 작성했다. 회사 소스, 내부 GitLab 이슈·MR, 운영 지표 및 현재 서비스 상태는 검토하거나 공개하지 않았다. 따라서 이 글은 당시 작성한 문제 분석과 선택의 기록이며, 비공개 구현을 재현하지 않는다.

## 출발점: UI를 바꾸지 않고 내부 상태 모델을 바꾸는 리뉴얼

리모트미팅은 기존 jQuery UI를 React와 Recoil 기반으로 전환한 화상 미팅 서비스 리뉴얼이었다. 초기 목표는 사용자 관점의 UI·기능을 유지하면서 내부 구현을 교체하는 것이었다. 하지만 MQTT에서 도착하는 layout 같은 집합 객체를 그대로 atom으로 다루면, 객체의 일부만 바뀌어도 그 atom을 읽는 컴포넌트가 다시 렌더링되는 문제가 드러났다.

이 프로젝트에서 중요한 질문은 “서버 메시지를 어떻게 덜 받을까”가 아니라, **집합 메시지를 받은 뒤 클라이언트가 어느 책임 경계까지 업데이트할 것인가**였다.

## 선택: 전송 단위와 화면 상태 단위를 같게 두지 않기

회고 Day2는 서버가 메시지 호출 수를 줄이기 위해 여러 attribute를 한 entity로 묶어 보낸다는 점을 전제로 한다. 그 전송 단위를 Recoil atom 하나에 그대로 보관하면 selector를 거쳐도 참조 컴포넌트의 렌더 범위가 넓어진다.

그래서 개선 방향은 다음과 같았다.

- 서버에서 온 집합 객체는 수신 경계로 유지한다.
- 화면에서는 단일 속성·단일 데이터 모델을 기준으로 상태를 나눈다.
- 컴포넌트는 자신이 그리는 모델 조각만 구독한다.
- 이전 값과 다음 값이 같으면 상태 업데이트 자체를 생략한다.

이는 메시지의 형태가 곧 화면의 책임이 되어서는 안 된다는 판단이다. Day0의 UserList 논의도 같은 문제를 다룬다. 사용자 단위 업데이트가 있을 때 관련 컴포넌트만 다시 그리는 것을 목표로 했고, 사용자마다 `atomFamily`와 effect를 만드는 방안은 인원 수만큼 이벤트가 생기고 기존 Map 기반 로직 변경 폭이 커질 수 있어 그대로 채택하지 않았다.

## 제작 중 마주친 문제와 수정

### 1. `atomEffect`가 상태 흐름의 중심이 되면서 생긴 제약

Day1은 `atomEffect`의 `onSet`이 effect 자신의 `setSelf()` 변경으로는 호출되지 않는 점을 기록한다. 또한 한 atom의 effect가 다른 atom에 관련 이벤트를 전달하려 할 때 제약을 만났다고 분석했다.

이 문제에서 선택한 방향은 effect에 흐름을 더 쌓는 것이 아니라, room/private 코드와 같은 방식으로 **상태 전용 hook을 분리**하는 것이었다. 컴포넌트가 `useRecoilCallback`이나 상태 setter를 통해 변경을 수행하는 경로는 effect 내부의 간접 이벤트보다 의존성과 호출 맥락을 드러내기 쉽다. 이 글은 당시 회고가 언급한 설계 방향을 정리한 것이며, 비공개 최종 코드의 구조를 주장하지 않는다.

### 2. event handler의 오래된 dependency와 state mismatch

Day4는 core module 이벤트를 구독하는 handler가 외부 상태에 의존하지만 dependency를 잘못 선언해 동기화가 어긋난 사례를 남긴다. 매 렌더마다 handler를 새로 만드는 방식은 피하고, 올바른 dependency를 주거나 `useRecoilCallback`의 `set`·`snapshot`을 이용해 **호출 시점의 상태를 읽고 갱신**하는 방향을 검토했다.

핵심은 hook 이름이 아니라 handler가 언제 생성되고 어떤 상태를 캡처하는지다. callback 밖에서 여러 Recoil state를 참조하는 구조는 dependency 목록을 넓히고, 이벤트 시점의 상태와 렌더 시점의 상태를 혼동하게 만든다.

### 3. 재사용하려 만든 custom hook이 렌더 원인을 숨긴 문제

Day5는 state·props가 바뀌지 않았는데도 컴포넌트가 다시 렌더링되는 현상을 추적하다 custom hook 내부의 전역 상태 의존을 발견한 과정을 기록한다. 주 컴포넌트는 단일 모델을 다뤘지만, hook은 여러 전역 상태를 읽어 단일 책임 경계를 넘었다.

대응은 custom hook을 없애는 것이 아니라, hook의 전역 상태 참조를 단일 모델 기준으로 다시 나누는 일이었다. 재사용성은 파일을 분리하는 것만으로 생기지 않으며, 구독 범위가 분명해야 렌더 원인도 추적할 수 있다는 교훈을 남겼다.

## 이력에서 읽은 제작의 흐름

1. **2022-03-07 · Day0** — UserList atom 구조와 사용자 단위 렌더링 목표를 정의하고 `atomFamily` 대안을 검토했다.
2. **2022-03-07 · Day1** — `atomEffect/onSet`과 atom 간 이벤트 전파의 제약을 분석했다.
3. **2022-03-09 · Day2** — MQTT layout entity와 렌더 범위의 충돌을 단일 속성 상태·컴포넌트 책임 분리로 풀었다.
4. **2022-03-10 · Day4** — callback dependency와 snapshot 시점 문제를 정리했다.
5. **2022-03-14 · Day5** — custom hook의 전역 상태 의존이 만든 불필요한 렌더 원인을 되짚었다.

## 재현 가능한 검증과 한계

공개 회고에는 React DevTools/프로파일링으로 불필요한 렌더링을 관찰하고 전후 동영상을 남겼다는 기록이 있다. 그러나 해당 동영상, 코드, 자동화 테스트를 여기서 재실행하지 않았으므로 수치나 성능 개선율을 인용하지 않는다. 이 제작기의 검증 범위는 회고에서 확인 가능한 문제·대안·선택이며, 현재 코드에 대한 검증은 아니다.
